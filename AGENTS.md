## Development Environment

The plugin runs inside a Docker Compose stack (WordPress + MySQL). Start it with:

```bash
docker compose up -d
```

WordPress is available at http://localhost:8080. The plugin directory (`lihi-short-url/`) is mounted directly into the container at `wp-content/plugins/lihi-short-url`, so file changes take effect immediately without rebuilding.

## Testing

Tests run inside Docker using a dedicated test database plus separate PHP 7.4 and PHP 8.2 PHPUnit containers built from official `php:*-cli` images. Composer must be run only inside those containers. Each PHP version mounts only `lihi-short-url/`, `tests/`, `patchwork.json`, and `phpunit.xml` read-only under `/app/code`, exposes its version-specific Composer file/lock as `/app/composer.json` and `/app/composer.lock`, and stores `vendor/` plus the WordPress core install in that service's Docker-managed `/app` volume. Dependency installs should not create `vendor-*` or `wordpress-*` directories in the repository working tree.

```bash
docker compose --profile test up -d --build --force-recreate --remove-orphans db_test phpunit74 phpunit82

docker compose --profile test exec phpunit74 composer install --working-dir=/app
docker compose --profile test exec phpunit74 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'

docker compose --profile test exec phpunit82 composer install --working-dir=/app
docker compose --profile test exec phpunit82 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'
```

The PHP 7.4 container covers the plugin's minimum supported PHP version; the PHP 8.2 container catches compatibility issues on a modern runtime. After the test profile is running, `make test` runs both containerized PHPUnit suites. `make coverage` runs both coverage targets; `make coverage74` and `make coverage82` generate coverage under `/app/coverage` in the matching container workspace.

## Packaging

GitHub Actions workflow `.github/workflows/package-plugin.yml` runs only on tag pushes. The package job builds `build/lihi-short-url.zip`, validates that the ZIP contains `lihi-short-url/lihi-short-url.php` and `lihi-short-url/readme.txt`, and uploads artifact `lihi-short-url-plugin`; the release job downloads that same artifact and publishes a GitHub Release for the tag. If a release for the tag already exists, the ZIP asset is replaced with `gh release upload --clobber`.

## Translations

Compile `.po` files to `.mo` binaries (requires `gettext` / `msgfmt`):

```bash
make          # compile all .mo files
make clean    # remove compiled .mo files
```

Translation files live in `languages/`. The WordPress.org slug and gettext text domain are `lihi-short-url`.

## Architecture

- `lihi-short-url/lihi-short-url.php` — plugin entry point. The header currently declares `Version: 1.0.2` and `Text Domain: lihi-short-url` (matching the WordPress.org slug). Non-admin requests are rejected via early `return`. Loads `bootstrap.php`. The plugin no longer calls `load_plugin_textdomain()` — once published on WordPress.org the directory auto-loads translations from the language pack, and self-hosted environments still pick up the bundled `.mo` files via WP's default loader.
- `lihi-short-url/readme.txt` — canonical WordPress.org readme. Includes `Stable tag` (currently `1.0.2`), `Tested up to`, `Requires PHP`, an `External services` section that discloses every outbound call to `app.lihidev.com` / `w.lihidev.com` (data sent + ToS / Privacy URLs) per WordPress.org guideline 9, the FAQ / Changelog rendered on the directory listing, and a Description note that the plugin is maintained at `weedgood/lihi-wp-plugin` on GitHub. This file is the source of truth for user-facing plugin metadata; the project root `README.md` is for developers.
- `lihi-short-url/LICENSE` — GPL-2.0-or-later full text. Matches the `License: GPLv2 or later` declared in the plugin header and `readme.txt`.
- `lihi-short-url/uninstall.php` — runs once on plugin deletion (when `WP_UNINSTALL_PLUGIN` is defined). Removes the three options (`lihi_email`, `lihi_domain`, `lihi_uuid`) and the JWT transient (`lihi_token`) so no plugin data lingers after uninstall.
- `lihi-short-url/bootstrap.php` — loads all includes in dependency order: helper → settings → exceptions → interface → client → stores → service → add-shorturl-column. Everything loads unconditionally; the plugin needs **two** options before its UI does anything — `lihi_email` AND `lihi_domain`. Bootstrap intentionally does **not** register dashboard-wide setup `admin_notices` for missing settings; UI hooks inside `add-shorturl-column.php` guard themselves on both options (see below), and the settings page remains available under Settings → lihi Short URL.
- `lihi-short-url/includes/config.php` — returns a flat array of plugin configuration values (`api_domain`). Loaded lazily by `lihi_config()` and cached for the request lifetime. The old `redirect_domain` and separate `auth_domain` keys have been removed — auth and short-URL calls now share the lihi Wordpress API under `api_domain`, while the per-site redirect domain comes exclusively from the `lihi_domain` wp_option (admin picks it from the profile selector). If the option is unset, `Lihi_Service::fetch_or_create()` forwards an empty string to the lihi API.
- `lihi-short-url/includes/helper.php` — namespace helpers: `lihi_config( $key )` (reads from `config.php`), `lihi_email()`, `lihi_domain()`, `lihi_uuid()`, `lihi_site_host()`, and `lihi_resolve_url()`. There are intentionally no global `lihi_client()` / `lihi_service()` wrappers; client, service, and store access must go through `Lihi_Singletons`.
- `lihi-short-url/includes/lihi-singletons.php` — `Lihi_Singletons`: request-lifetime singleton registry and dependency composition class. Static methods such as `lihi_client()`, `lihi_uuid_store()`, `lihi_token_store()`, and `lihi_service()` create / return shared instances; matching `*_set()` methods replace or reset instances for tests.
- `lihi-short-url/includes/settings.php` — registers the plugin settings page under Settings → lihi Short URL. The "Save & Verify" button fires `wp_ajax_lihi_update_email` (named function `Lihi\ShortUrl\ajax_update_email()`). Empty / whitespace-only input runs `delete_option('lihi_email')` and returns a "cleared" message, so admins can disable the plugin from the same form. Non-empty input must pass `sanitize_email()` + `is_email()` (rejects sanitized-but-malformed addresses) before it calls `Lihi_Client::update_email( $email )`; only on success is the option persisted via `update_option('lihi_email', ...)`, so an address the lihi service rejects never becomes active. The response payload is `{ verified: bool, message: string }` so the UI can render localized status inline; error JSON responses use explicit HTTP status codes (`403` permission, `400` validation, `429` rate limit, `503` service unavailable). `Lihi_Validation_Exception` / `Lihi_Rate_Limit_Exception` / `Lihi_Server_Exception` map to localized error messages (raw message logged via `error_log` on server errors only when `WP_DEBUG` is true). `$_POST['email']` / `$_POST['domain']` go through `wp_unslash()` before sanitization per WordPress coding standards. Page is always available regardless of whether email is configured. When the option is non-empty, `render_settings_page()` also calls `Lihi_Service::get_profile()` during render (same login-then-call pattern as the lihi button) to display the account's role, plan end date, and available redirect domains; the entire profile / error block is wrapped in `<div id="lihi-account-section">` so the JS can blank it out on every successful email save (otherwise a "verification email sent" or "cleared" response — both `verified: false`, no reload — would leave the prior account's data visible). `Lihi_Auth_Exception` (email not verified) / `Lihi_Server_Exception` render a localized inline `.notice-error` inside the same wrapper without blocking the page. Redirect domains are rendered as a `<select>` whose current selection persists to the `lihi_domain` option via the `wp_ajax_lihi_update_domain` handler (`Lihi\ShortUrl\ajax_update_domain()`) — empty input clears the option, anything not matching a basic hostname regex is rejected, membership in the profile's domain list is not re-verified on save (UI only offers valid domains; stale selections degrade gracefully because the API substitutes an account-valid domain when needed).
- `lihi-short-url/includes/client/lihi-client-interface.php` — `Lihi_Client_Interface`: unified contract for the lihi Wordpress API under `wordpress/v1`. Auth endpoints (`update_email()`, `login()`) do not take a bearer token; JWT endpoints (`get_profile()`, `get_sites()`, `get_short_links()`, `create_site()`) take `string $token` as first param. `POST /mail` (legacy api_key mail sender), `PUT/PATCH/DELETE /sites`, `/posts`, and the `/site-urls` family are not part of the plugin API contract. See `docs/lihi-api-endpoints.md` for the complete API reference, written as an API spec without internal source or documentation locations.
- `lihi-short-url/includes/client/lihi-client.php` — production HTTP client implementing the unified interface. The constructor receives `base_url` and site-scoped `uuid` from outside (the helper currently passes `lihi_config( 'api_domain' )` and `lihi_uuid()`), so the client does not read config or option-backed UUID state by itself. No token stored on the instance; each JWT method receives the token directly and passes it to `request()`. Auth requests strengthen identity checks by sending `email`, the WP site's host (from `home_url()`) as `hostname`, and the injected UUID as `uuid` in the JSON payload; login requests additionally send `is_mobile` from `wp_is_mobile()`. The plugin does not override the HTTP `Host` header because proxies / load balancers may rewrite it. Errors map to existing exceptions: 400 → `Lihi_Validation_Exception`, 403 → `Lihi_Auth_Exception`, 429 → `Lihi_Rate_Limit_Exception`, 500 / network → `Lihi_Server_Exception`.
- `lihi-short-url/includes/store/lihi-uuid-store.php` — `Lihi_Uuid_Store`: thin wrapper around the persistent site-scoped `lihi_uuid` option and option-backed `lihi_uuid_lock`. Exposes `get()`; it validates UUID v4, lazily creates the option on first auth use under a short DB-backed lock, waits for concurrent generators, replaces invalid stored values, and always reads back the persisted UUID after writes. It intentionally uses an option rather than a transient because this is stable site identity, not a cache.
- `lihi-short-url/includes/store/lihi-token-store.php` — `Lihi_Token_Store`: thin wrapper around the site-scoped `lihi_token` transient and `lihi_token_lock` wp_cache entry. Exposes `get()` / `set()` / `delete()` / `acquire_lock()` / `release_lock()` / `flush()`; the underlying cache keys live only here so callers never hard-code them. `flush()` polls for the login lock before deleting so an in-flight `login()` can't strand a stale JWT by `set_transient()`-ing after the delete.
- `lihi-short-url/includes/service/lihi-service.php` — `Lihi_Service`: business logic. Constructor takes `Lihi_Client_Interface` and `Lihi_Token_Store`; both are injected by `Lihi_Singletons::lihi_service()` so the service does not instantiate its own dependencies or read config. `login( $email )` calls `Lihi_Client::login( $email )` against the unified lihi Wordpress API and returns the bearer token. `get_token( $email )` (private) follows a three-step lookup: (1) store `get()`; (2) `acquire_lock()` — only the winner calls `login( $email )` and stores via `set()`, others poll for up to 3 s; (3) fallback login if the poll times out. Token cache is site-scoped (one lihi account per site) so every admin shares one JWT. On `add/update/delete_option_lihi_email`, `Settings.php` resets all per-account state — both `Lihi_Singletons::lihi_token_store()->flush()` and `delete_option('lihi_domain')` — so neither the JWT nor the saved redirect domain leaks across accounts. Both public methods — `get_profile()` and `get_or_create_short_url()` — share the same login-then-call pattern: read `lihi_email()` once, call `get_token( $email )`, forward the token to the client, and on `Lihi_Token_Invalid_Exception` invalidate the cached token and retry once with the same email. `get_or_create_short_url()`'s `fetch_or_create()` uses option/context helpers for the WP site host, target URL, and redirect domain; it namespaces the API `type` field as `"{type}:{host}"` (e.g. `post:example.com`) so the same `type_id` on different WP sites under one lihi account stays distinct, while the original `$type` is still used in `tags`.
- `docs/lihi-api-endpoints.md` — lihi API endpoint reference with request/response shapes and error mapping. It intentionally describes API behavior without exposing internal source or documentation locations.
- `lihi-short-url/includes/add-shorturl-column.php` — UI hooks (enqueue, column registration, attachment detail panel) are wrapped in `if ( lihi_email() !== '' && lihi_domain() !== '' )` so they only register when the plugin is fully configured. Enqueued button assets use the plugin release version (`1.0.2`) as their cache-busting version. Iterates every `public` post type on `admin_init` (skipping `attachment`) and registers a "Short URL" column with a lihi button for each; also registers the Media Library list-mode column via the `manage_media_columns` / `manage_media_custom_column` filter pair; adds a lihi button to the attachment detail panel via `attachment_fields_to_edit`. The AJAX handler `wp_ajax_lihi_copy_url` is always registered (as named function `Lihi\ShortUrl\ajax_copy_url()` so tests can invoke it directly). `$_POST['item_id']` is run through `wp_unslash()` before `intval()` per WordPress coding standards; the handler derives the actual item type server-side with `get_post_type( $item_id )` instead of trusting the client `data-type` / AJAX payload. After nonce and input validation, the handler requires `current_user_can( 'read_post', $item_id )`, so logged-in users may only generate short URLs for posts / attachments they can read. Error JSON responses use explicit HTTP status codes (`400` bad request / upstream validation, `403` permission or unverified lihi email, `409` plugin setup incomplete, `503` lihi service unavailable, `500` unexpected generation failure). Validation exception text is returned raw in the JSON payload because `lihi-button.js` renders it with `textContent`; server-side diagnostics use `error_log` only when `WP_DEBUG` is true so production hosts don't see plugin chatter.
- `lihi-short-url/assets/lihi-settings.js` — settings page button handlers. A shared `bindSaver()` helper POSTs each form's payload to admin-ajax (email → `lihi_update_email`, domain → `lihi_update_domain`) and renders an inline `notice` below the control: `.notice-success` with the server's localized message, or `.notice-error` with the server error message (text-only, `textContent`, never `innerHTML`). The email binding also passes an `onSuccess` hook that always blanks `#lihi-account-section` (so the prior account's role / end date / domain selector can never linger after switching emails) and, when the server returns `verified: true`, schedules `window.location.reload()` after a 2 s delay so the admin can read the "✓ Email verified" notice before the page repaints with `Lihi_Service::get_profile()` data fetched under the fresh JWT.
- `lihi-short-url/assets/lihi-button.js` — async delegated click handler for lihi buttons (uses `document` event delegation on `button[data-lihi]`). Module-level `lihiBusy` flag disables all `button[data-lihi]` on the page while a request is in flight, preventing concurrent clicks. Loading state and `lihiBusy` cleared in `finally`. Two independent delays: `resetDelay` (300 ms) governs how long buttons stay disabled; `labelDelay` (1200 ms) governs how long the "Copied!" label stays visible after a success. The original label ("lihi") is passed in via `lihiButton.labelOriginal` so the revert target is a config constant rather than DOM state — a rapid second click during the "Copied!" window cancels the pending timer and restores the original label from config before starting the new request. Errors surface as an auto-dismissing WP-style `.notice.notice-error` injected next to `.wp-header-end` (auto-removed after 5 s).

All hooks use anonymous functions registered directly via `add_action` / `add_filter`.
