## Development Environment

The plugin runs inside a Docker Compose stack (WordPress + MySQL). Start it with:

```bash
docker compose up -d
```

WordPress is available at http://localhost:8080. The plugin directory (`lihi-short-url/`) is mounted directly into the container at `wp-content/plugins/lihi-short-url`, so file changes take effect immediately without rebuilding.

## Testing

Tests run inside Docker using a dedicated test database plus separate PHP 7.4 and PHP 8.2 PHPUnit containers built from official `php:*-cli` images. Composer must be run only inside those containers. Each PHP version mounts only `lihi-short-url/`, `tests/`, `patchwork.json`, and `phpunit.xml` read-only under `/app/code`, exposes its version-specific Composer file/lock as `/app/composer.json` and `/app/composer.lock`, and stores `vendor/` plus the WordPress core install in that service's Docker-managed `/app` volume. Dependency installs should not create `vendor-*` or `wordpress-*` directories in the repository working tree.

```bash
docker compose --profile test up -d --build --force-recreate --remove-orphans db_test phpunit74 phpunit82

docker compose --profile test exec phpunit74 composer install --working-dir=/app
docker compose --profile test exec phpunit74 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'

docker compose --profile test exec phpunit82 composer install --working-dir=/app
docker compose --profile test exec phpunit82 sh -lc 'cd /app/code && /app/vendor/bin/phpunit -c phpunit.xml'
```

The PHP 7.4 container covers the plugin's minimum supported PHP version; the PHP 8.2 container catches compatibility issues on a modern runtime. After the test profile is running, `make test` runs both containerized PHPUnit suites. `make coverage` runs both coverage targets; `make coverage74` and `make coverage82` generate coverage under `/app/coverage` in the matching container workspace.

## Packaging

GitHub Actions workflow `.github/workflows/package-plugin.yml` runs only on tag pushes. The package job builds `build/lihi-short-url.zip`, validates that the ZIP contains `lihi-short-url/lihi-short-url.php` and `lihi-short-url/readme.txt`, and uploads artifact `lihi-short-url-plugin`; the release job downloads that same artifact and publishes a GitHub Release for the tag. If a release for the tag already exists, the ZIP asset is replaced with `gh release upload --clobber`.

## Translations

Compile `.po` files to `.mo` binaries (requires `gettext` / `msgfmt`):

```bash
make          # compile all .mo files
make clean    # remove compiled .mo files
```

Translation files live in `languages/`. The WordPress.org slug and gettext text domain are `lihi-short-url`.

## Architecture

- `lihi-short-url/lihi-short-url.php` — plugin entry point. The header currently declares `Version: 1.0.3` and `Text Domain: lihi-short-url` (matching the WordPress.org slug). Registers a deactivation hook that removes saved settings, the site UUID / UUID lock, and the cached JWT transient. Non-admin requests are rejected via early `return`. Loads `bootstrap.php`. The plugin no longer calls `load_plugin_textdomain()` — once published on WordPress.org the directory auto-loads translations from the language pack, and self-hosted environments still pick up the bundled `.mo` files via WP's default loader.
- `lihi-short-url/readme.txt` — canonical WordPress.org readme. Includes `Stable tag` (currently `1.0.3`), `Tested up to`, `Requires PHP`, an `External services` section that discloses outbound lihi calls (data sent + ToS / Privacy URLs) per WordPress.org guideline 9, the FAQ / Changelog rendered on the directory listing, and a Description note that the plugin is maintained at `weedgood/lihi-wp-plugin` on GitHub. This file is the source of truth for user-facing plugin metadata; the project root `README.md` is for developers.
- `lihi-short-url/LICENSE` — GPL-2.0-or-later full text. Matches the `License: GPLv2 or later` declared in the plugin header and `readme.txt`.
- `lihi-short-url/uninstall.php` — runs once on plugin deletion (when `WP_UNINSTALL_PLUGIN` is defined). Removes plugin-owned options (`lihi_email`, legacy `lihi_domain`, `lihi_uuid`, `lihi_uuid_lock`) and the JWT transient (`lihi_token`) so no plugin data lingers after uninstall.
- `lihi-short-url/bootstrap.php` — loads all includes in dependency order: helper → settings → exceptions → interface → client → stores → service → shorturl-column-ajax → add-shorturl-column. Everything loads unconditionally; the plugin only needs `lihi_email` before its lihi button UI registers. Bootstrap intentionally does **not** register dashboard-wide setup `admin_notices` for missing settings; UI hooks inside `add-shorturl-column.php` guard themselves on email only (see below), AJAX hooks inside `shorturl-column-ajax.php` always register, and the settings page remains available under Settings → lihi Short URL.
- `lihi-short-url/includes/helper.php` — namespace helpers: `lihi_api_host()`, `lihi_email()`, `lihi_uuid()`, `lihi_site_host()`, `lihi_passthrough_redirect_url()`, `lihi_home_url()`, `lihi_password_reset_url()`, and `lihi_resolve_url()`. `lihi_api_host()` directly returns the lihi app/API host; there is no separate config wrapper. There are intentionally no global `lihi_client()` / `lihi_service()` wrappers; client, service, and store access must go through `Lihi_Singletons`.
- `lihi-short-url/includes/lihi-singletons.php` — `Lihi_Singletons`: request-lifetime singleton registry and dependency composition class. Static methods such as `lihi_client()`, `lihi_uuid_store()`, `lihi_token_store()`, and `lihi_service()` create / return shared instances; matching `*_set()` methods replace or reset instances for tests.
- `lihi-short-url/includes/settings.php` — registers the plugin settings page under Settings → lihi Short URL. The "Save & Verify" button fires `wp_ajax_lihi_update_email` (named function `Lihi\ShortUrl\ajax_update_email()`). Empty / whitespace-only input runs `delete_option('lihi_email')` and returns a "cleared" message, so admins can disable the plugin from the same form. Non-empty input must pass `sanitize_email()` + `is_email()` (rejects sanitized-but-malformed addresses), include a password, and confirm account-creation consent before it calls `Lihi_Client::update_email( $email, $password )`; only on success is the option persisted via `update_option('lihi_email', ...)`, so an address the lihi service rejects never becomes active. The response payload is `{ verified: bool, message: string }` so the UI can render localized status inline; error JSON responses use explicit HTTP status codes (`403` permission, password invalid, unverified lihi email, or unavailable lihi account, `400` validation, `429` rate limit, `503` service unavailable). `Lihi_Validation_Exception` / `Lihi_Email_Or_Password_Invalid_Exception` / `Lihi_Rate_Limit_Exception` / `Lihi_Server_Exception` map to localized error messages (raw message logged via `error_log` on server errors only when `WP_DEBUG` is true). `$_POST['email']` goes through `wp_unslash()` before sanitization per WordPress coding standards. Page is always available regardless of whether email is configured. When the option is non-empty, `render_settings_page()` also calls `Lihi_Service::get_profile()` during render (same login-then-call pattern as the lihi button) to display the account's role and plan end date; successful profile details are wrapped in `<div id="lihi-account-section">` so the JS can blank prior account data on every successful email save. When no profile is available, the email/password form remains visible and `Lihi_Auth_Exception` (email not verified), `Lihi_User_Invalid_Exception` (`User Invalid` or JWT `user_not_found`, meaning the lihi account is unavailable), `Lihi_Token_Invalid_Exception` (JWT token invalid / expired / unexpected login-again errors after retry), and `Lihi_Server_Exception` render localized inline `.notice-error` messages in `.lihi-account-panel__messages` without blocking re-verification. Redirect-domain selection is no longer stored or rendered by the settings page.
- `lihi-short-url/includes/client/lihi-client-interface.php` — `Lihi_Client_Interface`: unified contract for the lihi Wordpress API under `wordpress/v1`. Auth endpoints (`update_email()`, `login()`) do not take a bearer token; JWT endpoints (`get_profile()`, `get_options()`, `create_passthrough_nonce()`, `get_sites()`, `get_short_links()`, `create_site()`) take `string $token` as first param. `GET /user/options` returns create-modal option data (`domains`, `utm_sources`, `utm_mediums`), `GET /site/find` returns a single short URL string in `data.site` for required WordPress `type` / `type_id`, and `POST /site/store` creates short links. Browser-facing `GET /passthrough/redirect` is not a client method because it creates a SaaS web session. `POST /mail` (legacy api_key mail sender), site update/delete, `/posts`, and the `/site-urls` family are not part of the plugin API contract. See `docs/lihi-api-endpoints.md` for the complete API reference, written as an API spec without internal source or documentation locations.
- `lihi-short-url/includes/client/lihi-client.php` — production HTTP client implementing the unified interface. The constructor receives `base_url` and site-scoped `uuid` from outside (the helper currently passes `lihi_api_host()` and `lihi_uuid()`), so the client does not read config or option-backed UUID state by itself. No token stored on the instance; each JWT method receives the token directly and passes it to `request()`. Auth requests strengthen identity checks by sending `email`, the WP site's host (from `home_url()`) as `hostname`, and the injected UUID as `uuid` in the JSON payload; login requests additionally send `is_mobile` from `wp_is_mobile()`. `create_passthrough_nonce()` posts browser-generated `challenge = base64url(sha256(verifier))` plus optional `target` to `/passthrough/nonce`; target is either an admin-relative path such as `/myDomain` / `/profile#utm-setting` or an absolute URL that lihi-admin converts to site search. The plugin does not override the HTTP `Host` header because proxies / load balancers may rewrite it. Errors map to typed exceptions: 400 → `Lihi_Validation_Exception`, 403 `email not verified` → `Lihi_Auth_Exception`, `User Invalid` or authenticated JSON `user_not_found ,please login again` → `Lihi_User_Invalid_Exception`, authenticated JSON `Token invalid ,please login again` / `Token expired ,please login again` / `Something wrong ,please login again` → `Lihi_Token_Invalid_Exception`, 429 → `Lihi_Rate_Limit_Exception`, 500 / network / unexpected JSON `result:false` → `Lihi_Server_Exception`.
- `lihi-short-url/includes/store/lihi-uuid-store.php` — `Lihi_Uuid_Store`: thin wrapper around the persistent site-scoped `lihi_uuid` option and option-backed `lihi_uuid_lock`. Exposes `get()`; it validates UUID v4, lazily creates the option on first auth use under a short DB-backed lock, waits for concurrent generators, replaces invalid stored values, and always reads back the persisted UUID after writes. It intentionally uses an option rather than a transient because this is stable site identity, not a cache.
- `lihi-short-url/includes/store/lihi-token-store.php` — `Lihi_Token_Store`: thin wrapper around the site-scoped `lihi_token` transient and `lihi_token_lock` wp_cache entry. Exposes `get()` / `set()` / `delete()` / `acquire_lock()` / `release_lock()` / `flush()`; the underlying cache keys live only here so callers never hard-code them. `flush()` polls for the login lock before deleting so an in-flight `login()` can't strand a stale JWT by `set_transient()`-ing after the delete.
- `lihi-short-url/includes/service/lihi-service.php` — `Lihi_Service`: business logic. Constructor takes `Lihi_Client_Interface` and `Lihi_Token_Store`; both are injected by `Lihi_Singletons::lihi_service()` so the service does not instantiate its own dependencies or read config. `login( $email )` calls `Lihi_Client::login( $email )` against the unified lihi Wordpress API and returns the bearer token. `get_token( $email )` (private) follows a three-step lookup: (1) store `get()`; (2) `acquire_lock()` — only the winner calls `login( $email )` and stores via `set()`, others poll for up to 3 s; (3) fallback login if the poll times out. Token cache is site-scoped (one lihi account per site) so every admin shares one JWT. On `add/update/delete_option_lihi_email`, `Settings.php` flushes the token store so stale JWTs do not leak across accounts. Public API calls share the same login-then-call pattern: `get_profile()`, create-modal `get_url_options()` (uses `GET /user/options` for domains plus UTM source / medium options), `get_or_create_short_url()`, Copy-only `get_existing_short_url()`, and passthrough `create_passthrough_nonce()` read `lihi_email()` once, call `get_token( $email )`, forward the token to the client, and on `Lihi_User_Invalid_Exception` invalidate the cached token and surface the unavailable-account error without retry; on `Lihi_Token_Invalid_Exception` they invalidate the cached token and retry once with the same email. `get_or_create_short_url()` checks `GET /site/find` for a non-empty `data.site` short URL, otherwise creates one using modal options: selected `domain`, selected tags only (front-end recommendations are not sent unless clicked), sent to the SaaS API as a comma-separated `tags` string, and UTM params appended directly to the destination URL; it does not send a separate `utm` object to the SaaS API. `get_existing_short_url()` never calls `create_site()`; when `data.site` is empty it throws `Lihi_Not_Found_Exception`. `create_passthrough_nonce()` sends the frontend-selected target with the browser proof challenge so the browser can redirect to lihi-admin's GET passthrough flow with nonce + verifier query params.
- `docs/lihi-api-endpoints.md` — lihi API endpoint reference with request/response shapes and error mapping. It intentionally describes API behavior without exposing internal source or documentation locations.
- `lihi-short-url/includes/shorturl-column-ajax.php` — AJAX endpoints for the Short URL column buttons. Always registers `wp_ajax_lihi_url_options`, `wp_ajax_lihi_create_url`, `wp_ajax_lihi_copy_url`, legacy `wp_ajax_lihi_edit_url`, and reusable `wp_ajax_lihi_passthrough_nonce` so stale buttons get JSON errors instead of WordPress's bare `0`. All handlers share the neutral `lihi_short_url` nonce, validate the selected item with `get_post_type( $item_id )`, require `current_user_can( 'read_post', $item_id )`, and reject empty `lihi_email` with HTTP 409; passthrough handlers additionally require `current_user_can( 'manage_options' )` before item validation. The options handler fetches domains plus `utm_sources` / `utm_mediums` from `GET /user/options` for the create modal, normalizing domains to `{ value, label }` and UTM options to `{ source, medium }`. The create handler requires a non-empty `domain` value but does not re-fetch or re-validate profile membership (the SaaS API decides whether the submitted domain is valid), parses JSON `tags` and JSON `utm`, calls `get_or_create_short_url()`, writes `update_post_meta( $item_id, 'lihi_already', '1' )`, and returns `{ url, lihi_already: true }`. The Copy handler only calls `get_existing_short_url()`; if the upstream short link is missing, it writes `lihi_already = 0` and returns HTTP 410 with `{ code: "lihi_missing", message: "Short URL has been removed. Please create it again." }`. The reusable Passthrough handler validates a browser-generated 43-character base64url challenge plus a scalar frontend-selected target (`/myDomain`, `/profile#utm-setting`, or an absolute URL), creates the nonce, and returns `{ nonce, redirect_url }` only. Error JSON responses use explicit HTTP status codes (`400` bad request / upstream validation / invalid browser challenge / invalid target, `401` lihi login session expired after token retry, `403` permission, unverified lihi email, or unavailable lihi account, `409` email setup incomplete, `410` upstream short URL missing, `503` lihi service unavailable, `500` unexpected generation/copy/edit failure), and common exception mapping is centralized in `handle_lihi_ajax_exception()`. Validation exception text is returned raw in the JSON payload because `lihi-button.js` renders it with `textContent`; server-side diagnostics use `error_log` only when `WP_DEBUG` is true so production hosts don't see plugin chatter.
- `lihi-short-url/includes/add-shorturl-column.php` — UI hooks (enqueue, column registration, attachment detail panel) are wrapped in `if ( lihi_email() !== '' )` so they register whenever an auth email is configured; the absence of `lihi_domain` no longer blocks button visibility. Enqueued button assets use `1.0.3-{filemtime}` cache-busting versions so split JS files cannot be mixed from browser cache after a local edit. Iterates every `public` post type on `admin_init` (skipping `attachment`) and registers a "Short URL" column for each; also registers the Media Library list-mode column via the `manage_media_columns` / `manage_media_custom_column` filter pair; adds a lihi field to the attachment detail panel via `attachment_fields_to_edit`. PHP intentionally outputs only an empty `.lihi-button-container` with `data-lihi-container`, `data-id`, `data-type`, and `data-lihi-already`; `lihi-button.js` appends the real button into that container and renders the visible label (`lihi` vs `Copy`).
- `lihi-short-url/assets/lihi-settings.js` — settings page button handler. A shared `bindSaver()` helper POSTs the email payload to admin-ajax (`lihi_update_email`) and renders an inline `notice` below the control: `.notice-success` with the server's localized message, or `.notice-error` with the server error message (text-only, `textContent`, never `innerHTML`, with a safe "Forgot password?" link only for structured password-invalid errors). The email binding also passes an `onSuccess` hook that always blanks `#lihi-account-section` (so the prior account's role / end date can never linger after switching emails) and, when the server returns `verified: true`, schedules `window.location.reload()` after a 2 s delay so the admin can read the "✓ Email verified" notice before the page repaints with `Lihi_Service::get_profile()` data fetched under the fresh JWT. The dashboard button opens a new tab through GET passthrough when the settings page has already produced a cached JWT; without a cached token it opens `https://lihi.io`.
- `lihi-short-url/assets/lihi-button-api.js` / `lihi-short-url/assets/lihi-button-modal.js` / `lihi-short-url/assets/lihi-button.js` — frontend Short URL button stack. WordPress 5.5 compatibility is preserved by enqueueing classic scripts with dependencies (`lihi-button-api` → `lihi-button-modal` → `lihi-button`) instead of ES modules. `lihi-button-api.js` owns the semantic admin-ajax facade (`loadUrlOptions(container)`, `createShortUrl(container, options)`, `copyShortUrl(container)`, `createPassthroughNonce(container, target, challenge, messages)`), so action names, nonce, item id/type payloads, target/challenge validation, JSON error parsing, and the 60-second domain / UTM options cache stay out of UI code. `lihi-button-modal.js` owns the centered fade create / notice / confirm modals, modal id constants, one shared select loading/render helper for domain and UTM source / medium, one Tags field with click-to-add recommended tag buttons plus removable selected chips inside the tag input, the Domain label-row "Custom domain?" action (manager passthrough to `/myDomain`, non-manager external link to `https://lihidomain.com`), the UTM source / medium row "Manage options?" action, separate confirm-before-dashboard messages for custom domains and UTM options, UTM collection, and confirm callbacks. `lihi-button.js` owns delegated clicks on JS-created `button[data-lihi]` and administrator-only adjacent `button[data-lihi-edit]`, button rendering inside empty `data-lihi-container` nodes, `data-lihi-already` label state (`lihi` vs `Copy`), copy/create/edit/dashboard-target flow orchestration, busy state, clipboard fallback prompt, opening the create modal only after `lihi_missing` copy errors, generating verifier/challenge for Edit and confirmed modal dashboard actions, selecting passthrough targets on the frontend (`/myDomain` for domain management, `/profile#utm-setting` for UTM settings, existing short URL for Edit), and opening lihi-admin's GET passthrough URL in a new tab with nonce + verifier query params.

All hooks use anonymous functions registered directly via `add_action` / `add_filter`.
